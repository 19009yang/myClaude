## 文件及可见范围

- `manifest.json`：宿主清单，含本地任务ID、任务路径、超时、资产映射和三组名称。
- `tasks/<id>/prompt.md`：任务Agent可见的正文。宿主将唯一占位符 `{{output_dir}}` 替换为本次隔离交付目录的绝对路径。
- `tasks/<id>/assets/`：复制到交付目录的输入文件；文件校验值在清单中记录。只有最后两题有此目录。
- `seed/sessions.json`：两套记忆系统共同接收的历史用户消息，宿主建库使用。
- `judge/<id>/rubric.json`：评分标准，每题100分，含首轮/最终评分所需规则和历史消息依据。
- `judge/<id>/follow_ups.json`：宿主在第2、3轮发出的固定用户消息，不增加隐藏事实。
- `judge/07_json_config_diff/expected_diff.json`：配置差异题的16条参考变更，仅评分器可见。
- `seed/evidence_index.json`：本地历史消息ID、会话、日期及正文校验值，仅宿主/评分器可见。
- `checksums.json`：冻结的文件清单与SHA-256；`validate.py`：无网络、无模型、无数据库写入的静态核查。

不要把本目录直接作为任务Agent的可读工作区。只向隔离运行环境投递渲染后的正文和对应输入资产。评分器、历史种子、参考答案、其它任务产物和其它组数据库都留在工作区外。仅改变cwd不足以实现文件访问隔离。

## 已完成的预处理

1. 历史种子由39条基础用户消息（H001至H039）与5条合成补充组成，共21个会话。消息和会话均使用本地编号；正文与日期供建库使用，评分依据通过本地消息ID关联。
2. 包含5条明确标记为 `synthetic_supplement` 的历史用户消息（S01至S05），补齐姓名生日、提醒方式、工作/日程、学习时长、项目边界和财务口径。它们是为任务约束准备的合成数据，并保留显式标记。两套记忆系统必须接收同一份；不能直接给某组写入标准答案或预生成记忆。
3. SQL第5章统一设为多表连接；窗口函数作为后续学习内容。后续补充明确覆盖此前含糊日程和旧的一次性待办；全部消息按文件数组顺序处理。
4. 固定评测时钟为2025-03-26、Asia/Shanghai。生日按下一次发生日期计算：父亲2026-03-20、母亲2025-08-05；不考年龄。下次理疗是2025-04-01；SQL排期为2025-03-31至04-06；季度计划为2025-04-01至06-30。
5. 统一离线、Markdown文件交付；不要求真实账号、外部消息发送、Notion同步或真实日历API。缺少的诊所、负责人、期限、流水金额明确留待确认，防止用编造事实得分。
6. 每题设置评分权重、目标阈值及历史证据，明确固定输出名。代码题补全异常处理契约，规定标准库unittest；配置题补全JSON输出结构和整数组替换规则。
7. 三组都使用两条无新增事实的固定追问。这里的3轮指3个用户任务轮次，每轮内部可以有多个模型/工具调用，二者需要分别限制和记录。

## 建库与运行协议

建议在同一myClaude Agent上比较 `none`、`legacy`、`lamemory`，统一主模型、普通工具、静态Skill、输入/输出预算及随机性设置。统一允许的上下文预算；各后端在预算内采用自身的召回方式，不强行要求相同记忆注入长度。系统提示使用共同任务规则，记忆部分由各适配器提供。

1. 为两套记忆系统建立各自空存储，按 `seed/sessions.json` 的session与消息顺序处理历史。每条用户记录作为一个完整建库轮次：写入该用户原文后，由宿主追加固定助手确认“已收到。”，再走各后端正常的轮次提交/提取流程。确认仅用于结束轮次，不提供新事实。保留种子消息ID到运行时消息ID的映射；更换session时只重置会话历史，继续共享同一用户的长期记忆。禁止把全部种子直接拼到测试会话上下文。每个后端记录自己的提取用量、失败与重试，待任务全部处理成功后分别冻结存储快照。
2. `none`组不导入种子，保留当前任务内完整历史，禁用长期记忆注入、检索、写入及跨会话历史读取。泛用题也使用同样的组设置：有记忆组保留同一初始记忆，从而观察无关记忆干扰。
3. 每个独立任务及每次重复均克隆对应组的冻结快照，新建测试session和空工作区。历史种子、评分答案不可作为可读文件投递。不要在任务之间共享新产生的事实、文件或judge反馈。
4. 将manifest列出的assets按destination原样复制到交付目录，渲染prompt中的路径。发送初始正文，保存首轮产物与完整轨迹。依次发送两条固定追问，保存每轮产物快照；固定跑满3轮，阈值与“最早达标轮次”事后计算，避免组间反馈不一致。单轮超时按manifest执行，内部工具调用次数由运行器另设共同上限；失败应记录，不能记为0次成功的通过结果。
5. 独立评分器按相同rubric评首轮及各后续轮。基于历史的信息核对 `source_message_ids`；新增建议与已发生事实须区分。代码题应在隔离环境实际执行；不要只让模型声称“测试通过”。生日/排期/金额也应核对实际日期与算术。

当前 `core/memory.py` 是LaMemory兼容入口，不是第二套独立后端。`legacy`应使用已冻结的旧Markdown算法实现；本目录不恢复旧算法、不更改任何真实记忆库，也未执行三组对照。

## 评分与结果记录

每条criterion设置max_score，并标为 `memory`（明确依赖历史）、`mixed`（历史与任务质量混合）或 `general`。分别报告三类得分/可得分；混合项不能当纯召回准确率。目标阈值在各题rubric中定义，不要只比较通过率。

至少保存组别、后端/模型/配置哈希、任务与种子哈希、重复序号、每轮正文/输出文件/工具轨迹/分项得分、超时和错误、模型调用数、总耗时与tokens。Agent、记忆提取、摘要、用户消息处理和judge分开计量；建库成本与任务在线成本分开报告。初始建议8题×3组×3次重复，共72次任务运行（每次最多3个用户轮次）。

这些任务评估跨会话事实与偏好在任务中的使用，没有设计训练/测试分割或经验晋升流程，不能据此宣称程序经验迁移有效。

## 静态验证

在myClaude根目录运行：

```bash
python3 benchmarks/memory_task/validate.py
```

核查任务数量、全部文件校验值、资产、评分总分、消息依据、公开/私有路径、固定追问以及配置参考变更是否与实际输入一致。验证只证明资产包一致，不代表模型能够完成任务或三组性能有提升。若有意修改资产，应审阅差异并发布新版本后重新冻结校验值。
