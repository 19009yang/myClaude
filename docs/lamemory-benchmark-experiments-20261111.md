# LaMemory 记忆检索与上下文预算实验汇总

日期：2026-11-11。本文汇总当日的生日提醒排查、查询对照、方案 C 全量测试、编程题补跑，以及旧系统接入发送前压缩后的独立重跑。

本报告所称 **LaMemory** 为 Layered Aggregated Memory；`legacy` 为项目冻结的旧记忆实现，`none` 为无长期记忆组。实验任务的模拟基准日期为 **2025-03-26（Asia/Shanghai）**，与本报告日期不同。任务在本地离线产出文件，不操作真实日历、购物或其他外部账号；“真实实验”指实际请求聊天模型和 embedding 服务。

## 1. 主要结论

1. **最初缺少父亲生日属于召回遗漏。** 数据库中已经有 active 生日事实和有效向量；含交付要求的查询经过融合排序后没有把该事实放入前 10 条。清理查询后，后续生日测试由 57.5 分提升到 95 分，但两次独立运行重新建了记忆，不能将全部提升严格归因于查询清理。
2. **固定快照对照证明，这道生日题上“事实需求查询”比只加检索指令更有效。** 父亲生日语义排名由 71–72 提升到 28，再提升到 4；母亲由 58–59 提升到 30，再提升到 2。原查询并非低于 0.3 阈值，而是被前 30 条候选限制排除。
3. **LaMemory 方案 C 在六道记忆相关题上全部完成并通过，最终均分 95.17。** 合并注明配置差异的编程补跑后，8 题中有 7 题完整完成；JSON 配置对比题第三轮因执行模型输出截断失败，不能用其已有产物的 100 分宣称完整成功。
4. **旧系统接入发送前压缩后，输入超限问题在本次重跑中消失。** 最新独立重跑有 5/8 题完整通过，0 次 `BudgetError`、0 次评分失败；13 次压缩尝试中，11 次提交、2 次回滚。剩余三题分别因摘要 JSON 解析错误或执行模型输出截断未完成。
5. **旧系统压缩重跑的 99 分是 5 个成功样本的条件均分，不等于全量表现。** 它不能直接与 LaMemory 六道记忆题的 95.17 分比较。不同阶段还改变了评分窗口和评分模型推理配置，完成率改善不能全部归因于压缩。
6. **当前方案 C 是人工固定查询实验。** 没有验证自动查询改写器，也没有通过多次独立任务重复建立统计显著性。现有结果支持继续改进和验证，不支持认定某个记忆系统在所有任务上全面胜出。

## 2. 统计口径与共同设置

### 2.1 三类结果需要分开

| 指标 | 本报告采用的定义 |
|---|---|
| 轮次执行成功 | `status=complete` |
| 有效轮次分数 | 执行成功，且 `grade.status=complete` |
| 任务完整完成 | 初始请求和两次固定复查，共三轮执行与评分全部成功 |
| 任务通过 | 完整完成，且最终评分达到该题 rubric 阈值 |
| 失败后的产物分 | 仅作诊断；不作为有效轮次或完整任务成功的依据 |
| 首轮/最终均分 | 只覆盖对应位置上具有有效分数的样本，必须同时标明样本数 |

三轮复查是同一次任务运行内的迭代，**不是三个独立样本**。除查询向量对照外，各题均只有一次独立重复。

早期探路报告的统计逻辑与后续版本不同，个别汇总曾包含失败轮次留下的产物分。本文不把这些旧汇总直接并入当前有效样本统计，原文件保持不变。

### 2.2 设置

| 项目 | 设置或说明 |
|---|---|
| 聊天、记忆、评分模型 | 报告记录为 DeepSeek `deepseek-flash` |
| LaMemory embedding | `Qwen/Qwen3-Embedding-4B`，2560 维 |
| LaMemory 检索 | keyword + cosine 候选，RRF 融合；关闭 rerank 与关键词降级 |
| 常用候选参数 | 关键词 30、语义 30、最终 top-k 10；cosine 阈值 0.3；RRF k=60，两路等权 |
| 记忆引用预算 | 2048，另受总输入预算约束 |
| Agent 窗口 | 32768；除最早探路外，输出预留 8192、安全余量 512，输入预算 24064 |
| 每轮调用限制 | 最多 8 次 Agent 调用、24 次工具调用 |
| 任务工具 | 本地 read/write/ls/python；Python 在代码隔离中执行 |
| 主动记忆工具、静态 Skill | 三组均关闭；测量自动提取与上下文注入 |
| 评分配置 | 原主线窗口 32768；编程补跑与最新旧系统重跑改为 65536，评分推理关闭 |
| 更大评分窗口的影响 | 评分输入预算由 24064 增至 56832；Agent 的共同预算仍为 24064 |
| 冻结快照 | 同一运行内每题克隆初始存储；补跑通过哈希校验复用原种子快照 |

`hybrid` 是 LaMemory 的检索设置。旧系统仍全量注入 Markdown 长期记忆，`none` 不读长期记忆；两者不会因此执行 embedding 检索。

表中 Agent 窗口指 benchmark 的共同预算。E5、E6 将模型配置的 `context_window` 声明为 65536，以允许更大的评分请求，但 `settings.context_window` 仍为 32768，Agent 实际输入预算仍为 24064；这不是给某组 Agent 额外输入空间。

## 4. 查询清理：E1 → E2

E1 的检索查询在用户生日请求后，还包含“输出 birthday_reminders.md”“下一次发生日期”“不要求计算年龄”等交付要求。中文双字片段和常见词产生额外匹配，例如“输出”匹配工作报告目标，“下一”匹配下一版 PRD，“前提”片段匹配“前提交”。

父亲生日已存入 active 长期记忆，向量索引也存在。E1 首轮复算关键词排名第 2，但语义候选未包含它；RRF 对两路同时命中的条目叠加分数，父亲生日最终落在前 10 条之外。母亲生日进入了当时的融合第 5。

E2 按公开提示段落提取任务请求，并排除两条固定无新事实复查提示。实际用于检索的文本为：

> 帮我在日历上加一下我爸妈的生日提醒，我老是忘。要提前提醒我好准备礼物。

| 组别 | E1 三轮分数 | E2 三轮分数 |
|---|---|---|
| none | 25 → 34 → 25 | 24 → 25 → 24 |
| legacy | 100 → 100 → 100 | 100 → 100 → 100 |
| LaMemory | 57.5 → 58 → 57.5 | 95 → 95 → 95 |

E1 首轮关键词候选 22 条，E2 为 7 条；E2 首轮父亲、母亲生日进入融合第 6、9。三轮复用同一任务查询，查询 embedding 请求由 3 次降至 1 次。

**解释限制：**E1、E2 分别重新执行记忆提取，种子条目数量和措辞有差异，不能把 37.5 分提升当作严格配对的单变量效应。该阶段确认了查询清理实际生效，以及后一次任务中生日事实正常进入上下文。

## 5. 固定同一份快照的查询对照：E3

### 5.1 三组定义

E3 使用 E2 的同一份 LaMemory 种子数据库和原有文档向量，不重新建库，不提取记忆，不生成摘要，不运行主任务或评分模型。固定快照 SHA-256 为：

```text
b26198b3c2313954118007feade173f4ee32fc5598995d586a67fdbcda9dcecc
```

| 方案 | 关键词输入 | embedding 输入 |
|---|---|---|
| A：raw | 清理后的原请求 | 清理后的原请求 |
| B：instruct | 与 A 相同 | 检索指令 + 原请求 |
| C：facts | 事实需求查询 | 与 B 相同的检索指令 + 事实需求查询 |

事实需求查询为：

> 父亲和母亲的姓名、生日日期、生日提醒偏好，以及相关礼物待办

它没有填入姓名、具体生日、提前天数、购物渠道或具体礼物等答案。检索指令为：

```text
Instruct: Given a user's request, retrieve personal facts, preferences, and pending tasks needed to fulfill it.
Query: <查询>
```

三次重复轮换请求顺序，不使用本地查询向量缓存。原始向量、完整语义排名、候选过滤原因及融合结果均保存在各次结果 JSON 中。

### 5.2 结果

| 方案 | 父亲语义排名，三次 | 父亲平均 cosine | 母亲语义排名，三次 | 母亲平均 cosine | 融合排名：父亲/母亲 |
|---|---|---:|---|---:|---|
| A | 72、72、71 | 0.413890 | 59、58、58 | 0.426680 | 6 / 9 |
| B | 28、28、28 | 0.419714 | 30、30、30 | 0.418643 | 4 / 5 |
| C | 4、4、4 | 0.470705 | 2、2、2 | 0.488793 | 2 / 3 |

- A 的两条生日均高于 0.3 阈值，但语义排名在 30 之后，被候选宽度截断；最终依靠关键词路进入融合前 10。
- B 使两条事实进入语义候选，但母亲恰在第 30 名边缘。母亲 cosine 比 A 略低而排名更好，说明不能只看绝对分数，应同时看其他候选和相对排名。
- C 使两条生日稳定进入语义前 4。仅针对这两条目标事实，语义前 10 覆盖率为 A=0、B=0、C=100%；三组最终融合前 10 的目标覆盖率则都为 100%。

因此，该对照证明了本题语义排名改善，而不是三组最终任务分数的变化；也不能将两条目标事实的覆盖率解释为全部相关记忆的 Recall@10。

### 5.3 查询改写的副作用与额外离线复算

C 的关键词候选由 7 条增加到 21 条，“待办”等通用词引入竞品报告、SQL 练习等内容。额外使用 C 已保存的查询向量、把关键词查询改回 A 原请求做离线复算，三次均得到：

- 关键词候选恢复为 7 条。
- 母亲、父亲生日融合排名分别为 2、3。
- 竞品报告和 SQL 练习退出前 10，但仍有项目依赖等噪声。

该组合可称为后续待验证方案 D：**关键词用原请求，语义用事实需求查询**。它没有额外 API 请求，也没有正式全量任务结果；不能把这次离线复算写成已经完成的在线方案 D 评测。

## 6. 方案 C 全量与编程补跑：E4、E5

E4 在主 benchmark 中显式启用 `retrieval_query_mode=facts`。八条改写均来自预先审阅的公开请求，并绑定公开提示的 SHA-256；两道编程题仅提取公开技术要求。任务 Agent 仍收到完整原始要求，只有 LaMemory 的检索输入改变。默认 `request` 模式并未被全局替换。

E4、E5 的种子快照哈希完全一致。E5 不重新建库，仅在新目录重跑两道编程题；评分窗口从 32768 提高到 65536，并关闭评分模型推理。Agent 仍使用共同的 32768 窗口和原推理设置。

六道记忆相关题全部通过，首轮均分 **96.33**，最终均分 **95.17**。八题合并观察时有 **7/8** 完整完成，但不同评分配置下不计算一个无条件总均分。

JSON 题在 E4 首两轮因评分输入超出 24064 无法评分，第三轮触发费用预算；E5 首两轮正常得到 100，第三轮执行模型返回 `output_truncated`。第三轮已有文件获诊断分 100，因执行失败而不计入完整成功。

### 6.1 主要内容缺口

- **生日提醒：**按摩仪尚未购买的待办没有丢失，但后续版本放在独立关联事项中，没有放入生日事件备注；按既定 `gift-note` 口径扣 5 分。
- **SQL 安排：**已保存的“每周最多 6 小时”未稳定注入，最终产物把它降级为假设；第 5 章多表连接与后续窗口函数的澄清也被重新描述为待确认。首两轮曾注入章节信息，最后一轮相关原子事实没有继续出现在上下文中。
- **季度计划：**已保存的设计心理学方向、UI 沟通实践等未进入检索/摘要覆盖，计划偏重 SQL、Python 和独立跑数。长期产品目标、与研发相关实践也不完整，最终为 84。
- **项目风险：**大部分背景与依赖已覆盖，接口依赖未单列造成少量失分。

这些缺口说明，改善查询不能代替复杂任务的多事实覆盖和跨轮证据保留。

## 7. 原旧系统为何大量“不通过”

原适配器完整拼入长期记忆和会话，发送前超过 24064 就抛 `BudgetError`。旧压缩函数虽存在，但主要在轮次结束后依据 usage 和约 90% 总窗口阈值触发，与发送前预算的计数和时机不一致。

若六道记忆题取 E4、两道编程题取 E5，则旧系统只有生日题完整完成；并不代表其余题产物普遍不达标。例如 SQL 首轮 93、项目风险 97、财务 100、代码评审 100，但后续流程因上下文超限或评分异常中断。

原阶段有 6 个不同任务出现旧系统输入超限；JSON 题在 E4、E5 各出现一次。另有评分模型输出截断、编程题评分证据包超限，均应与记忆召回缺失分开解释。

## 8. 旧系统压缩独立重跑：E6（最新结果）

### 8.1 改动与控制条件

- 复用 E4 同一份 legacy 冻结种子；与 E5、E6 记录的逐文件快照哈希核对一致。
- 旧系统仍全量注入长期记忆，复用冻结原 `compress()` 和原摘要提示词，没有加入 LaMemory 的关键词或向量召回。
- 每次发送前按完整输入估算检查，在输入预算的 85%（20454）附近触发。必要时摘要当前轮已完成的工具组；保留当前用户请求，保持工具链完整。
- 原始会话单独追加归档；无效摘要、逾期响应或无缩减会回滚当次会话视图和长期记忆更新，并保存审计记录。
- 评分窗口 65536、评分推理关闭；Agent 输入预算仍为 24064。该评分设置与 E5 相同，与 E4 不同。

### 8.2 逐题结果

| 任务 | 压缩旧系统三轮结果 | 是否完整通过 | 剩余问题 |
|---|---|---|---|
| 父母生日 | 90 → 95 → 95 | 是 | 按摩仪待办放置位置，最终扣 5 分 |
| 理疗日程 | 100 → 100 → 100 | 是 | 无 |
| SQL 学习安排 | 100 → 100 → 100 | 是 | 无 |
| 项目风险看板 | 100 → 100 → 100 | 是 | 无 |
| 季度学习计划 | 96 → 96 → 执行失败 | 否 | 第三轮 Agent 输出截断；已有产物诊断分 92 |
| 财务复盘 | 100 → 执行失败 → 跳过 | 否 | 第二轮摘要响应 JSON 解析失败；已有产物诊断分 100 |
| JSON 配置对比 | 执行失败 → 跳过 → 跳过 | 否 | 第一轮摘要响应 JSON 解析失败；已有产物诊断分 100 |
| 代码评审 | 100 → 100 → 100 | 是 | 无 |

E6 的完整通过率为 **5/8 = 62.5%**。有效首轮均分 **98.00（7 题）**，有效最终均分 **99.00（5 题）**。24 个轮次槽位中，18 轮有效成功、3 轮失败、3 轮跳过。

本次 **没有 `BudgetError`，没有评分失败**。还存在 2 次宿主 JSON 解析错误和 1 次 Agent 输出截断，因此不能称为全量成功。

### 8.3 压缩实际发生了什么

| 任务 | 成功提交 | 失败回滚 | 输入估算变化示例 |
|---|---:|---:|---|
| 生日、理疗 | 0 | 0 | 未发生压缩 |
| SQL 学习安排 | 1 | 0 | 21742 → 8081 |
| 项目风险看板 | 1 | 0 | 25944 → 10239 |
| 季度学习计划 | 3 | 0 | 23825 → 9531，另两次也有缩减 |
| 财务复盘 | 0 | 1 | 21184，摘要解析失败后回滚 |
| JSON 配置对比 | 0 | 1 | 26345，摘要解析失败后回滚 |
| 代码评审 | 6 | 0 | 24283 → 12491，另五次也有缩减 |
| **合计** | **11** | **2** | **13 次尝试** |

可复核的实例：[SQL 摘要记录](../.myclaude/benchmarks/run-20261111-172154-845153/runs/03_sql_study_blocks/repeat-1/legacy/private/compression/test-03_sql_study_blocks-1-legacy/0001.json)、[项目风险摘要记录](../.myclaude/benchmarks/run-20261111-172154-845153/runs/04_project_risk_kanban/repeat-1/legacy/private/compression/test-04_project_risk_kanban-1-legacy/0001.json)、[财务摘要回滚](../.myclaude/benchmarks/run-20261111-172154-845153/runs/06_finance_review/repeat-1/legacy/private/compression/test-06_finance_review-1-legacy/0001.json)。两次失败的当前会话文件哈希、MEMORY.md 内容均与对应压缩前记录一致，回滚实际生效。

E6 共 144 次调用，其中摘要 13 次，摘要费用 **0.231505 CNY**，占本轮总费用约 **6.76%**。摘要用量日志中的 provider 调用成功与宿主 JSON 解析失败是不同层次：两次解析失败仍有实际调用费用，并未被记为零成本。

### 8.4 剩余故障的解释

1. **财务题在 21184 时仍低于硬输入预算 24064。** 预防性压缩失败导致整轮停止，说明当前实现还会把原本可发送的请求变成失败。后续可考虑：保留错误审计、受限重试；若原视图仍在硬预算内则暂缓压缩，真正超限时才要求摘要成功后继续。不能无条件忽略摘要错误后发送超限请求。
2. **两次 `JSONDecodeError` 只能确认摘要响应不符合当前 JSON 解析要求。** 原始摘要响应正文未在现有审计中完整保存，不能断言就是代码围栏、空响应或某一种具体格式；需要补充脱敏原始响应留档和明确校验规则。
3. **季度计划的输出截断来自 Agent，不是评分模型。** 增大评分窗口并关闭评分推理无法解决它。Agent 的输出/推理预算应作为下一轮独立变量评估。
4. **理疗题没有实际压缩。** 它从旧阶段评分失败变为三轮成功，不能归因于压缩；评分配置稳定化及生成变化都可能参与。

| 观察项 | LaMemory C：E4+E5 | 压缩旧系统：E6 |
|---|---|---|

| 主要剩余流程失败 | JSON 题 Agent 输出截断 | 两题摘要 JSON 解析失败；季度题 Agent 输出截断 |
| 信息覆盖缺口 | SQL 约束/澄清、设计心理学和相关实践等 | 成功的 SQL、项目题为满分；整体仍有流程缺口 |

当前共同完成的四道记忆题为生日、理疗、SQL、项目风险：C 最终均分 96.75，压缩旧系统 98.75。但两阶段评分窗口和评分推理设置不同，且只有一次独立重复，**这 2 分差不能归因为记忆算法本身**。

现有证据更适合支持以下判断：

- 查询的“任务动作”与“所需事实”表达差异会影响本题的语义排序，固定快照实验给出了直接证据。
- 上下文预算适配是旧系统可运行性的关键问题，最新真实压缩记录与零 `BudgetError` 支持这一判断。
- 全量记忆配合压缩能在部分任务中保留更全面的信息；LaMemory 的有限召回仍需要多事实覆盖检查。
- 摘要模型和主模型的格式、输出预算也会决定完成率，不能把所有失败都算作记忆内容错误。
- 当前不能仅比较成功样本均分，也不能从单题改写收益推导所有任务或自动改写器的收益。

## 11. 下一轮建议

1. **优先修复摘要响应的可诊断性与恢复路径。** 保存脱敏原始响应，校验 summary 和 memory_update，限制格式恢复与重试次数；预警阈值触发失败、但原请求未超硬预算时，允许明确记录的暂缓策略。
2. **统一稳定评分配置。** 固定足够容纳证据包的评分窗口和推理设置，分开记录执行失败、评分失败、产物得分，避免比较时再改变评分器。
3. **评估 Agent 输出截断。** 在同样快照和任务上独立测试推理配置或输出预留，保留失败响应与费用，不通过静默接受不完整回复制造成功。
4. **验证查询覆盖与跨轮事实保留。** 针对 SQL 限时、章节更正、季度多方向学习等建立来源可核对的覆盖检查；单独评估 D，以及只接收公开请求的自动改写器。
5. **再做同协议重复对照。** 复用固定种子，保持任务、评分、预算和模型设置一致，每题增加独立重复。同步报告完成率、有效样本数、分数、费用、摘要次数与延迟。
