# LaMemory 完整任务对照协议 v2

更新：2026-11-12。协议标识：`lamemory-task-comparison-v2`。

## 目的与判断边界

分别观察长期记忆带来的任务质量增益、相对旧系统的改进，以及相对完整历史原文的信息损失与资源收益。不预设 LaMemory 必须在所有任务得分最高；期望通过质量、完成率、tokens、费用和延迟共同评估。

沿用冻结的 8 道开发题、44 条用户种子、固定追问和评分标准。新协议不修改任务、rubric、checksums 或历史报告。尚未执行新四组真实模型对照；离线假模型分数为占位值。

## 四组的准确含义

| 组 | 历史输入 | 建库与维护 |
|---|---|---|
| none | 无历史种子，仅当前测试会话 | 无长期记忆调用 |
| legacy | 模型按相同历史顺序提取，完整注入积累的 Markdown | 提取，追加式更新；runtime 另有会话压缩 |
| full_history | 全部历史用户原文、日期、种类；来源编号由宿主保留 | 不提取、不摘要、不建向量；每次 Agent 请求重发全部原文 |
| lamemory | 检索事实及分层摘要，受 top-k/记忆预算约束 | 提取、摘要、文档/查询 embedding |

完整历史组从共同 `seed/sessions.json` 原样保留用户正文和数组顺序，不读取评分表、证据索引或参考答案。固定的助手确认“已收到。”没有历史事实，故不重复注入；这里定义的是完整历史**用户原文**基线，不是任意真实会话日志回放。历史作为参考数据注入，保留旧值及后续更正供模型判断，不直接写入标准答案。不保证该组必然取得最高分。

新建库采用 `dated-user-content-v2`：legacy、LaMemory 和完整历史组均收到同样的原文、日期和记录种类；历史消息/会话编号只保存在宿主来源记录中，不嵌入模型可见的历史包装。LaMemory 提取的 `source_message_ids` 只能使用提取请求最外层的运行时 `message_id`；正文中偶然出现的编号不构成合法来源，也不自动映射到其他消息。来源校验、批次原子性和重试上限保持不变。

此变更消除了 `dated-user-record-v1` 同时展示历史编号与运行时编号的歧义。2026-11-12 首次真实试跑在 H034 来源校验失败，但旧记录没有保存模型提取正文，不能追溯其具体非法 ID。原报告保留；新格式仍需真实模型重跑验证，离线复现不是在线成功证明。

继续保留原文 `content_sha256`、实际回放 `replay_sha256` 和历史 ID → 运行时 ID 映射；复用旧快照则记录源协议的输入格式，不冒充新版建库。

种子每组只构建一次，每题/每次重复克隆冻结快照并创建新会话；任务间不共享新记忆或评分反馈。完整历史组的当前任务消息独立归档，不回写种子原文。

任务包 manifest 中的三组名称属于冻结的历史资产声明；实际运行组由 Settings/report 声明。旧三组快照不包含 full_history，因此不能直接用于默认四组的 `--seed-from`；应新建四组快照，或仅选择源报告已有的组。

## 两种当前会话策略

默认 `shared_strict` 用于控制变量：各组都保留当前任务的完整用户、助手与工具消息，不做会话摘要、不丢弃旧轮次、不缩短工具结果。LaMemory 仍按其记忆预算选择历史事实/摘要，但选入后不能通过总预算裁剪再次让出空间。legacy 的发送前/轮次后会话压缩均禁用，即使 `legacy_preflight_compression=true`。

超出共同输入预算时明确抛出 `BudgetError`，保留原始消息及产物，归类为 `context_capacity`。这测量固定容量下的表现；容量不足不等于事实回答错误。质量对照应先选择足以容纳题目和会话的共同窗口；容量压力实验可以单独降低窗口，不静默增加某一组的预算。

`runtime` 保留各后端的产品行为：legacy 使用原摘要及预算适配，LaMemory 使用运行时工作视图/裁剪，none/full_history 超限失败。这比较整体运行能力，包含会话管理差异，不应将分差全部归因于长期记忆召回。不同策略的结果不合并。

普通 LaMemory 运行时仍默认 `overflow_policy=trim`；评测的 shared_strict 显式使用 `overflow_policy=error`。新增接口不改变普通聊天的默认行为。

## 共同条件

- 相同 Agent 模型、完整公开任务、工具 schema、输入/输出上限、每轮模型/工具调用上限及超时；禁用主动记忆工具、静态 Skill 和 M3 自动经验学习。
- 两套记忆后端使用相同的记忆模型及原始种子顺序，允许自身的提取/聚合算法不同，独立记录建库成本。
- 三个用户轮次固定执行，独立评分器的反馈不提供给任务 Agent。组执行顺序按 `(任务序号 + 重复序号 - 1) % 组数` 轮换，记录实际启动顺序。
- 新配置 `fair-comparison.json` 使用四组、3 次任务重复、65536 Agent/评分窗口、固定评分推理关闭和默认原请求查询。CLI 默认仍为 32768 Agent 窗口，所有组同预算；评分窗口也可独立配置。
- 模型配置声明的窗口不足时，在付费请求前拒绝运行，不根据模型名称猜测窗口。token 容量检查仍为保守 UTF-8/3 估算，实际用量优先使用 provider usage。

每次重复使用同一组冻结种子，仅测量任务生成波动；它不包含重新提取记忆的随机性。要评估端到端建库波动，需要另做独立建库重复并单独报告。

## 分数与缺失样本

报告保存全部 `planned_runs`。每组区分计划、已启动、未启动任务；预算在建库或中途耗尽时，未启动样本仍可见，但不被描述为记忆错误。

| 字段 | 含义 |
|---|---|
| execution_complete_runs | 三轮执行/记忆维护全部成功，不依赖 judge 是否成功 |
| execution_failed_runs | 已启动但未执行完三轮 |
| judge_failed_runs | 至少一个轮次评分出错，可与执行失败重叠 |
| unscored_execution_complete_runs | 三轮执行成功，但缺少完整有效评分 |
| complete_runs | 三轮执行及评分全部成功 |
| first_mean_score/final_mean_score | 对应位置执行和评分成功的条件均分，紧邻显示 scored_*_runs |
| final_pass_rate | 三轮完整且最终达标的任务数 / 已启动任务数 |
| planned_final_pass_rate | 同一已确认通过数 / 全部计划任务数；预算中断时不是最终效果估计 |
| failure_causes | 上下文容量、记忆维护、超时、供应商错误类型、评分错误及前序失败跳过等轮次计数 |

执行失败后留下的产物分为 `artifact_only=true`，保留用于诊断，不进入有效分数或配对。评分错误不阻止后续合法用户轮次，但会使完整评测失败。轮次指标、任务指标和未启动样本使用不同分母，不互相替代。

`paired_comparisons` 对每对组按相同 task_id/repeat 配对，分别比较首轮和最终分数。既输出全部题目，也按任务的 memory/mixed/general 类别输出；每个样本另保留评分维度分数。只有双方该位置的有效评分同时存在时才计入；公开缺失的 ID、执行状态、评分状态。分差为左组减右组，附配对数、独立题目数和分差标准差，不据此宣称统计显著。

最终配对同时附上这些相同样本的完整在线用量及平均费用，避免将失败早停产生的低费用解释为成本优势。首轮配对不附整项任务的费用。配对统计仍可能有幸存样本偏差，必须结合计划覆盖率、执行完成率和失败分类判断，不能只看成功样本均分。

## 成本口径

`cost_breakdown` 按组列出 build、online、judge 三阶段的调用数、输入/输出 tokens、费用及估算调用数，并保留按题/重复的 online 用量。

- build：一次性提取、摘要及文档向量索引。
- online：Agent、在线提取、摘要、索引维护及查询向量，是任务运行成本。
- judge：评测开销，独立列出，不纳入产品运行成本。
- `build_plus_workload_cost`：本次账本的建库加在线总额。使用 `--seed-from` 时 `seed_cost_included=false`，不能解释为历史建库免费；需要从源报告另取建库费用后按真实任务量摊销。
- 失败和缺 usage 的请求继续计入费用，并标明估算来源。离线模式 `usage.cost=0`；cost_breakdown 标为 simulated，仅验证记账路径。

`memory_responses/` 在每次记忆模型返回后、JSON 解析及来源校验前保存请求和响应正文/usage；`usage.jsonl` 的 `memory_response` 指向对应文件。运行密钥脱敏，不保存请求头或思考字段。API 返回成功不代表提取校验成功，校验及重试结果仍以 seed_jobs/memory_jobs 为准；两者通过运行时消息 ID 关联。旧报告缺少的正文无法补造。

不要把不同完成数量、不同运行轮次、不同模型/窗口的总费用直接比较为效率。最终质量和费用首先使用相同配对样本，再报告失败消耗及全体覆盖。

## 使用与后续范围

```bash
.venv/bin/python -m benchmarks.memory_benchmark estimate --config benchmarks/memory_benchmark/fair-comparison.json
.venv/bin/python -m benchmarks.memory_benchmark smoke --repeats 1
.venv/bin/python -m benchmarks.memory_benchmark run --config benchmarks/memory_benchmark/fair-comparison.json --prices /absolute/prices.json --max-cost 10
```

第一条不调用模型；第二条使用临时隔离的运行目录和假模型；第三条会发送付费请求。默认实际建库和任务数据均在新建评测目录，不改写真实会话。

这 8 题仍是开发集。人工 facts 查询属于公开请求的人工改写实验，不代表自动改写器；调参题的分数不能当作独立验收结果。更大历史规模、未参与调优的新验收集、自动查询改写、事实更正/遗忘任务仍需单独定义和冻结。当前代码未伪造这些任务或运行结果，也不宣称程序经验迁移收益。
