# LaMemory 开发指南（myClaude 初版）

版本：v0.1 草案

日期：2026-11-09

适用范围：个人开发、单机运行、以 Python 为主的 myClaude 项目。

**Layered Aggregated Memory（简称 LaMemory）** 是 myClaude 的记忆系统名称。本文定义适合个人项目的开发任务：以结构化记录为基础，逐步形成主题摘要和用户概览，并通过检索与预算管理支持长期使用。

**状态说明：M0–M3 的关键词模式单机运行时已实现。M2/M3 本次完成离线行为验证；此前 DeepSeek `deepseek-flash` 的真实记忆 smoke 只验证 M0/M1，不能作为 M2/M3 的真实模型或效果证据。具体接口、启用方式与限制见 [使用与验证](lamemory-usage.md) 及 [M2/M3 开发交付](lamemory-m2-m3.md)。embedding 和完整对照评测尚未实施。**

配套文档：[LaMemory 架构与实施方案](lamemory-design.md)。

## 1. 开发目标与版本边界

### 1.1 用户应该获得的能力

第一版完成后，用户可以：

- 在一个会话中提供偏好或事实，在新会话中被正确回忆。
- 明确要求“记住这件事”，并立即查看保存结果。
- 更正已有信息，让后续回答使用新信息，同时保留更新依据。
- 查询、修改或忘记一条记忆。
- 查看助手本次使用了哪些记忆，以及它们来自哪段对话。
- 在长期使用后，仍将提示词控制在模型的上下文预算内。

“原始对话留档”“长期记忆”“当前会话摘要”是三类不同数据。压缩会话不应删除原始证据，长期记忆也不应只是会话摘要的另一个名称。

### 1.2 分阶段范围

| 阶段 | 必须交付 | 完成标志 |
|---|---|---|
| M0：基础修复 | 路径与会话隔离、现有压缩错误修复、回归用例 | 现有聊天流程稳定，测试不会修改真实记忆 |
| M1：首个可用版本 | 结构化记忆、原文证据、提取、主动保存、检索、更新/删除、上下文预算 | 可以跨会话正确使用和管理记忆 |
| M2：分层整理 | 用户概览、项目/主题摘要、增量刷新、简化离线整理 | 记忆增多后仍可按需加载，并能传播变更 |
| M3：经验学习 | 经验候选、反馈、晋升、检索复用 | 经过验证的经验能帮助后续任务 |

M1 可以先以关键词模式打通闭环；正式宣称支持语义召回前，需要接入真实 embedding 并完成对应验证。M1 交付时要明确支持的模式及限制。

初版暂缓：多数据库后端、跨机器同步、复杂多租户权限、复杂阶段调度、自动主题聚类，以及自动生成并安装 Skill。单用户运行仍要保留 `user_id` 与 `session_id`，便于隔离测试和未来扩展。

## 2. LaMemory 的分层聚合设计

| 数据层次 | 职责 | 引入阶段 |
|---|---|---|
| 原始对话 | 保留消息与工具交互，为记忆提供可追溯证据 | M1 |
| 结构化记录 | 保存事实、偏好、事件、状态和版本，支持更新与检索 | M1 |
| 主题摘要 | 按项目或主题聚合相关记录，按需加载 | M2 |
| 用户概览 | 聚合稳定偏好和重要背景，提供简短导航 | M2 |
| 经验记录 | 保存有适用条件和结果依据的可复用做法 | M3 |

聚合结果保存来源 ID 和版本；摘要不能替代原始证据。来源更新或删除后，关联摘要要标记失效并重建。当前会话工作上下文独立管理，只在预算内选择所需历史与记忆。

LaMemory 的实现遵循以下原则：

- 原始记录、派生记忆和工作上下文分别存储。
- 轮次提交与主动保存各有明确的时机和幂等规则。
- 先保证关键词检索、版本更新和来源返回，再增加语义召回。
- 整理任务可重试、可观察；每次报告保存成功都对应实际持久化结果。
- 模块职责和依赖保持符合单机 Python 项目的规模。

```text

    store.py                      # SQLite、事务、查询和迁移

    extraction.py                 # 原始对话 → 候选记忆
    conflicts.py                  # 去重、更正和版本替代
    retrieval.py                  # 召回、融合和过滤
    context.py                    # 上下文预算与工作摘要
    jobs.py                       # 持久化任务与重试
    providers.py                  # chat / embedding / token 接口
    migrations/
      001_initial.sql
    hierarchy.py                  # M2 新增
    consolidation.py              # M2 新增
    procedural.py                 # M3 新增
tests/
  lamemory/
    fixtures/
    test_store.py
    test_ingest.py
    test_conflicts.py
    test_retrieval.py
    test_context.py
    test_migration.py
    test_chat_integration.py
```

依赖方向：Agent / 工具 → `LaMemoryService` → 业务模块 → Store / Provider。业务模块不依赖终端 `input()` 或全局 `shared`；provider 不读写业务表；工具不直接拼 SQL。

优先使用 Python 自带 SQLite、JSON、dataclass 和日志。Store 先保持一个清晰模块，出现实际复杂度后再拆 DAO。向量扩展、常驻 worker 和独立服务均按需要引入。

现有 `Memory.add_message()` 和 `build_context()` 保留，但最终仅负责转发。不要长期同时运行两套自动提取逻辑。

## 5. 数据结构与一致性规则

### 5.1 M1 最小表集合

| 表 | 必要字段 | 关键约束 |
|---|---|---|
| `lamemory_sessions` | user_id、session_id、created_at | 以 user_id + session_id 唯一定位 |
| `lamemory_messages` | message_id、user_id、session_id、turn_id、seq、role、payload_json、created_at | user_id + session_id + seq 唯一；保留工具调用结构 |
| `lamemory_items` | memory_id、user_id、scope_kind、scope_key、type、content、content_hash、slot_key、occurred_at、status、revision、superseded_by、origin、created_at、updated_at | 状态和可见范围显式；ID 与引用必须校验用户归属 |
| `lamemory_sources` | user_id、memory_id、message_id | 保存来源关系，使用同用户约束或复合外键 |
| `lamemory_jobs` | job_id、user_id、session_id、turn_id、kind、idempotency_key、status、attempts、available_at、last_error、payload_json | 同用户内 idempotency_key 唯一 |
| `lamemory_suppressions` | user_id、scope_kind、scope_key、source_key、slot_key、content_hash、created_at | 阻止被忘记的内容从旧来源自动重新提取 |
| `lamemory_migrations` | version、applied_at | 迁移按版本执行 |

检索索引是可重建投影。关键词索引和向量索引不能成为唯一事实来源。

### 5.2 记忆记录示例

以下为建议输出格式：

```json
{
  "memory_id": "lam_001",
  "user_id": "local-user",
  "scope_kind": "user",
  "scope_key": "local-user",
  "type": "preference",
  "content": "用户希望开发相关回答优先使用中文。",
  "slot_key": "response.language.development",
  "origin": "explicit",
  "occurred_at": null,
  "status": "active",
  "revision": 1,
  "superseded_by": null,
  "source_message_ids": ["msg_010"]
}
```

初版只支持 `fact`、`preference`、`event` 三类。无法确定的事件发生时间保持 null，不用记忆写入时间代替。`scope_kind` 先支持 user 与 session；项目范围由 M2 增加。

`slot_key` 表示可更新的事实位置，例如“项目的包管理器”。事件通常不适合按 slot 覆盖；两次出差可以同时成立。用户身份、会话 ID、记录 ID、状态和时间戳由宿主生成或校验，不能直接信任抽取模型填写的值。

### 5.3 写入和状态规则

- 原始消息成功保存后，才允许触发提取；提交完整轮次与创建提取 job 在一个事务中完成。
- 重复提交同一 turn 不新增 job；retry 沿用原幂等键，不重新生成来源 ID。
- 内容哈希只用于辅助去重，不能把不同时间的同类事件折叠成一次。
- 记忆状态采用 `active → superseded` 或 `active → deleted`；已替代与已删除项不参与默认召回。
- 更正时用事务创建新记录、更新旧状态和替代关系，避免同时暴露两个相互排斥的当前事实。
- 调用模型时不持有数据库写事务；得到并校验结果后再短事务提交。
- M1 单进程消费任务。若以后支持并发，需要原子 claim、任务租约和版本检查，再启动多个 worker。

SQLite 连接启用外键，设置合理的 busy timeout。默认数据目录建议为 `<project>/.myclaude/lamemory/`，加入 Git 忽略；基准测试始终使用独立运行目录。

### 5.4 建议配置项

以下默认值只作为初次实现的起点，可在小型验证集上调整：

| 配置 | 建议初始值 | 说明 |
|---|---|---|
| `database_path` | `<project>/.myclaude/lamemory/lamemory.sqlite3` | 使用绝对解析后的路径；测试显式覆盖 |
| `user_id` / `session_id` | 宿主提供 | 用户标识跨会话稳定；新会话生成新 session_id |
| `retrieval_mode` | `keyword` | 接好 embedding 后再允许配置为 `hybrid` |
| `top_k` | 5 | 召回上限，仍受预算限制 |
| `memory_token_budget` | 2048 | 召回记忆的初始上限，不包含全部对话预算 |
| `context_window` / `reserved_output` | 按实际模型配置 | 必须满足输出预留和输入预算约束 |
| `max_extracted_items` | 8 | 单轮自动提取条数上限 |
| `provider_timeout_seconds` | 30 | 模型请求时间上限；还要约束客户端内置重试 |
| `job_max_attempts` | 3 | 包含首次执行，耗尽后标记 failed |
| `auto_process_jobs` | 开发时显式选择 | 启用时在回复展示后有界消费；关闭时手动处理 |
| `project_id` | null | M2 的宿主项目标签，限制项目记忆和经验的可见范围 |
| `max_summary_chars` | 1200 | M2 分层摘要的字符上限，仍受提示词 token 预算约束 |
| `auto_learn_experiences` | false | M3 是否在完整轮次提交时投递经验候选任务 |
| `experience_min_successes` | 2 | M3 独立用户/测试成功证据门槛，不计训练轨迹或模型自评 |
| `max_experience_candidates` | 3 | M3 单轮经验候选上限 |

业务配置不保存明文密钥，provider 从单独的环境配置取得凭据。各评测组独立构造 provider 和配置对象，避免运行中修改全局环境变量造成串组。

## 6. 对外接口与 Agent 生命周期

### 6.1 接口职责

以下为接口契约，参数类型和返回对象在实施时定义：

| 接口 | 职责 |
|---|---|
| `append_message(message)` | 保存原始消息，不触发递归提取 |
| `commit_turn(turn_id)` | 标记完整轮次并幂等投递提取任务，与模型 usage 无关 |
| `store(content, source_message_ids)` | 显式保存；返回保存、重复、冲突或失败结果 |
| `search(query, filters, top_k)` | 返回可见的 active 记忆、分数、来源和检索模式 |
| `update(memory_id, content, source_message_ids)` | 根据用户更正创建新版本或新记录 |
| `forget(memory_id)` | 使该项失效、清理检索投影并增加防重新提取标记 |
| `inspect(memory_id)` | 返回版本、状态和来源；供调试或用户查看 |
| `build_context(system_prompt, budget)` | 构造合法模型消息，返回预算与召回诊断 |
| `process_pending(max_jobs)` | 有界地执行待处理任务；保存错误和重试状态 |
| `flush(timeout)` | 等待指定范围任务完成，返回完成/失败/超时及剩余数量 |

`LaMemoryService` 创建时绑定 `user_id`、`session_id`、配置与 provider。Agent 工具不接受任意 user_id，所有按 ID 操作也要校验归属。

### 6.2 一轮对话的数据流

```text
用户输入 → append_message
    ↓
检索相关记忆 → build_context → call_llm
    ↓
assistant 有 tool_calls？
    ├─ 是：保存 assistant → 执行工具 → 保存 tool → 继续模型调用
    └─ 否：保存最终回复 → commit_turn → 展示回复
                                      ↓
                            有界消费提取任务或稍后手动处理
```

检索以当前用户请求为主，避免每次工具循环都用工具输出重做相同检索。显式保存或更正后，可以使当前轮召回缓存失效。

M1 的任务消费放在主回复展示之后，采用有限调用时间和有限次数。失败时保留 job，下次重试；不会让整个 ChatNode 重跑。M2 如需消除等待，再引入单个后台 worker。

`flush()` 成功应表示目标任务已完成且查询可见；存在失败或超时必须返回明确信息。M2 加入摘要任务后，要扩展其等待范围，不能只等结构化记录就报告所有层级已更新。

### 6.3 主动记忆工具

第一版建议提供：

- `lamemory_store(content)`：用户明确要求记住的信息。
- `lamemory_search(query)`：查找相关记忆。
- `lamemory_update(memory_id, content)`：更正已保存内容。
- `lamemory_forget(memory_id)`：忘记指定项。

工具内部绑定当前用户与来源，工具定义与执行器通过同一实例注册。保存结果要区分“已生效”与“已排队”；不能在后台失败时仍向用户报告已记住。

初版的 forget 表示停止使用该记忆，原始会话留档仍保留。若用户要求删除原始对话，应使用单独的删除流程，并处理来源关系和派生记忆。显式重新记住同一内容时，允许在有新用户指令的情况下解除对应抑制，不能因普通旧消息重放而解除。

## 7. 提取、冲突和检索策略

### 7.1 提取

输入是一轮完整对话中的必要内容。优先提取用户提供的事实与明确偏好；助手推测、模型思考过程、普通工具日志不自动成为用户事实。任务结果进入程序经验学习时另走 M3 路径。

抽取结果采用结构化 JSON，至少检查：数组类型、最大条数、内容长度、允许的 type、来源 ID 是否属于本轮，以及时间字段是否合法。模型返回错误结构时有限重试，最终保留失败 job，不静默当作“没有新记忆”。

主动保存的内容也经过校验。自动提取应跳过已经由同一轮主动保存工具提交的相同事实，并忽略记忆工具回显，避免“记忆被再次记住”。

### 7.2 去重与更正

按以下顺序处理：

1. 同一来源或幂等键：直接返回已有结果。
2. 同用户、同范围、同类型的完全相同内容：复用已有记忆并补充来源。
3. 相同 slot 的明确更正：新记录替代旧记录。
4. 疑似重复或冲突：保留为待裁决候选；不强行覆盖当前事实。

初版只自动处理明确更正，复杂语义合并后置。用于“当前情况”的召回不混入待裁决冲突；历史查询可以返回旧版本并明确标记时间和状态。

### 7.3 检索

关键词模式先实现可重复的检索，再增加真实向量召回：

```text
请求与时间条件
  → 限定用户、scope、状态与时间
  → 关键词召回 / 可选向量召回
  → 融合与去重
  → 相关性排序，必要时考虑时间
  → 按记忆预算打包
  → 返回 memory_id、内容、证据和模式
```

中文检索要准备同义表达和中文短句样本，不能假定 SQLite 默认分词即可满足要求。首版可定义统一的分词预处理，验证后接 FTS；向量数量较少时可先在隔离后的候选上计算相似度，后续再换索引实现。

向量记录关联 memory_id、内容版本、embedding 模型标识与维度。更换模型或内容后重新构建；不得混用不同模型空间的向量。embedding 不可用时返回关键词降级模式，不能用随机或伪向量替代正式语义检索。

时间衰减用于辅助排序，不自动使长期偏好失效。明确失效、替代和归档优先使用状态，而不是仅凭年龄降低分数。

## 8. 上下文预算和失败处理

预算关系：

```text
允许输入 = 模型窗口 - 输出预留 - 安全余量
实际输入 = 系统提示 + 工具定义 + 当前请求 + 历史/摘要 + 召回记忆
```

建议为召回记忆设置独立上限，并保留近期完整轮次。模型窗口与输出预留从配置读取，不能继续固定为所有模型通用的 128000。

超预算时按顺序：减少低相关记忆 → 移除较旧的工作摘要或将历史压缩 → 对超长工具结果生成有限视图。原始结果继续留档。压缩以完整轮次和工具调用链为边界，不能产生缺少 tool_call 对应关系的消息。

系统提示、工具定义或当前请求本身就超预算时，应返回可处理的预算错误。Token 估计需包括消息包装和工具 schema；无法精确计量时标记为估算并预留余量。

召回记忆属于参考数据，来源内容不能提升为新的系统指令。原始用户指令与召回证据应分区表达，避免历史文本改变当前工具权限或运行约束。

| 失败情况 | 预期行为 |
|---|---|
| 提取模型超时或 JSON 无效 | 保留原文和任务；有限重试；主回复继续可见 |
| embedding 不可用 | 关键词检索，记录降级模式 |
| 摘要生成失败 | 保留原有工作视图，不用空摘要覆盖 |
| 主动保存失败 | 工具返回错误，不报告保存成功 |
| SQLite 写入失败 | 不报告持久化成功；主回复可展示，但明确本轮未保存 |
| 重复启动或任务重试 | 幂等消费，不重复新增事实 |

M1 对短期缓存和长期任务分别记录状态，不把所有异常吞掉。错误结果应能在调试界面或命令中查看。

## 9. 旧数据迁移

旧 `session.jsonl` 与 `MEMORY.md` 只作为导入源。路径修复前，还要识别 POSIX 上可能存在的带反斜杠文件名；不要假设数据一定在 README 中描述的目录。

迁移步骤：

1. 接受显式输入路径，生成只读预览：消息数、非法行、记忆条目数和目标用户/会话。
2. 备份原文件，记录文件哈希和导入批次 ID。
3. 导入 JSONL，保留 tool_call_id、tool_calls 与角色；非法行单独报告。
4. 将 MEMORY.md 条目标记为 `legacy_import`。没有可靠来源的条目不伪造 source_message_id，也不推断事件时间。
5. 验证历史恢复、条目数量、来源和重复导入行为。
6. 默认关闭原来的 Markdown 自动提取/追加；需要查看 Markdown 时从数据库导出。

第二次导入同一批次不应新增消息或记忆。回滚通过切回旧后端和原始备份完成，迁移不改写原文件。

## 10. M2 与 M3 的扩展方式

### 10.1 M2：分层摘要与简化整理

新增 `lamemory_summaries` 和摘要来源关系，区分 `profile` 与 `topic`。主题起初手动指定或使用固定项目标签；用户概览只保留稳定背景和主题导航。

每个摘要保存来源记忆 ID、源版本/哈希、摘要版本和 dirty 状态。来源被更新或删除后立即标记失效；重建完成前不注入仍含过期内容的摘要，可以回退到有效结构化记录。

整理命令先支持：处理积压任务、精确去重、应用已确定的失效状态、重建脏摘要、输出结果统计。不先引入自动聚类和复杂阶段调度。

已实现：`hierarchy.py`、`consolidation.py`、迁移 `002_hierarchy.sql`。通过 `refresh_summaries()` 或 `consolidate()` 建立用户概览/固定项目摘要，`define_topic()` 管理手动主题；后续写入在同一事务内标脏并投递幂等重建任务。摘要来源包含记忆 ID、revision 与哈希，发布前复核快照。`flush()` 同时等待当前会话任务和用户级摘要任务，并追踪期间新增的摘要代次。未配置分层摘要 provider 时使用有长度限制的原文摘录。

### 10.2 M3：程序记忆

经验结构建议包含任务类型、适用条件、步骤、结果依据、用户反馈、成功/失败计数和状态。

```text
完成任务 / 收到纠正
  → 提取经验候选
  → 记录独立使用结果与反馈
  → 达到预设证据门槛或经用户明确认可
  → 晋升为可检索经验
```

单次模型自评不能作为验证成功的唯一依据。同一轨迹重放不能累加为多次成功。错误经验支持撤销和版本替代。先保存为结构化经验；是否导出为 SKILL.md 是后续独立功能。

已实现：`procedural.py`、迁移 `003_procedural.sql`。已完成轮次可手动投递经验提取，或通过 `auto_learn_experiences=True` 启用自动投递。默认需要两个独立任务中的用户/测试成功证据，或可信宿主提交用户明确认可，才能晋升；模型自评和训练轨迹不计独立成功。同一版本链上的同一反馈轨迹只记录一次。有效经验进入关键词检索及上下文，失败反馈使其撤销，替代版本从 candidate 重新验证。未实现自动 Skill 生成/安装及真实模型迁移效果评测。

## 11. 测试与验收

测试按可观察行为组织，使用临时数据库、固定时钟和 fake provider。真实模型评测与离线功能测试分开。

| 验收场景 | 预期结果 |
|---|---|
| 用户 A 保存事实后开启新会话 | 召回该事实并返回原始来源 |
| 用户 B 查询相同问题 | 看不到 A 的记忆、来源和摘要 |
| 两个 session 各有临时要求 | session 范围要求不会跨会话生效 |
| 同一完整轮次重复提交 | 不重复建 job，不重复增加记忆 |
| 用户更正偏好 | 当前检索返回新版本；旧版本可追溯 |
| 两次不同日期的同类事件 | 两条事件都保留，时间查询可区分 |
| 忘记后重放旧来源 | 不重新生成被忘记内容 |
| 空查询、无匹配、超长文本 | 返回约定结果或错误，不越过预算 |
| 压缩包含多次工具调用的历史 | 请求中的工具消息关系仍完整，原文可恢复 |
| 提取、摘要或 embedding 故障 | 按失败策略运行，任务可检查和重试 |
| 进程中断后重启 | 已提交数据保留，待处理任务能继续 |
| 旧文件重复导入 | 导入结果稳定，源文件未变化 |

建议增加一个小型人工标注集：约 20 条事实/偏好/事件，配套直接问法、改写问法、冲突、时间和无答案查询。固定来源 ID 与期望结果；语义改写用例在 embedding 启用模式单独验收。

建议测试入口，待测试目录创建后执行：

```bash
uv run python -m unittest discover -s tests/lamemory -p 'test_*.py'
```

M1 发布条件：必需行为用例通过、迁移可预览和回滚、聊天工具循环可用、检索模式可观察、失败不会虚报保存成功，并完成一组真实模型的小规模验证。此处不预设准确率提升。

## 12. LaMemory 基准评测计划

### 12.1 首先提取无交互 Agent runner

提供与终端 UI 分离的运行入口，绑定独立工作区、会话、模型配置和记忆后端。runner 至少支持创建会话、发送消息、工具循环、有界超时、用量汇总和关闭。

无人值守运行不能等待 `input()`；需要确认的工具操作返回明确的未执行状态。任务与 judge 使用独立环境，模型不得读取评分标准、参考答案或其它组的记忆库。运行 cwd 只是路径设置，不能替代执行环境隔离。

### 12.2 对照组与任务范围

| 组 | 设置 |
|---|---|
| `none` | 同一 myClaude Agent，保留任务内历史，关闭跨会话记忆 |
| `legacy` | 旧 Markdown 算法；记录必要的路径与运行错误修复 |
| `lamemory` | 本指南实现的系统，记录功能阶段和启用项 |

各组使用同一原始记忆来源、主模型、工具、预算和评分协议。不要把更换 Agent 框架带来的差异全部归因于记忆。

在 `benchmarks/lamemory/tasks/` 建立 6–10 个资产齐全、无需外部账号的初始任务，覆盖依赖记忆、部分依赖记忆、记忆不适用和通用任务。冻结所选路径与文件哈希；通过 smoke 后再扩大样本。此目录需要在实施评测时创建。

每个任务从相同的初始记忆快照开始；同一任务内保留迭代历史和产物。测试答案、judge 反馈和上一任务产生的事实不能流入下一独立任务。持续学习能力另设有训练/测试划分的协议。

### 12.3 指标与后续基准

- 任务结果：首轮/最终得分、通过率、达到目标的轮数、超时和错误率。
- 记忆行为：有标注样本上的 Recall@k、更新正确性、来源覆盖、删除生效及隔离测试。
- 资源：检索延迟、总运行时间、上下文大小、模型调用与用量。
- 成本分类：Agent、提取、摘要、embedding、rerank、用户模拟和 judge 分别计量；区分建库与在线成本。

M2 稳定后增加历史会话问答评测；M3 完成后增加经验迁移任务，训练阶段积累经验，测试阶段每题使用同一个冻结训练快照。普通任务高分不能证明经验学习已有效。

LaMemory 的任务格式建议包含 `task_id`、`prompt`、`seed_messages`、`rubric`、`max_rounds` 和 `timeout`。仅向任务 Agent 提供 prompt 与正常工具，初始化消息由运行器导入，评分标准由独立评分器读取。评测报告保存运行清单、配置哈希、输出、分项得分与用量；不将其它实现的专属数据模型或服务接口作为运行前提。

## 13. 第一批开发任务与完成清单

建议按以下顺序拆分提交，每次提交包含对应验证说明：

1. **修复现有记忆基础问题**：路径、参数、隔离、压缩类型错误和失败传播；添加回归用例。
2. **建立 SQLite 存储与导入器**：lamemory_messages、lamemory_items、来源、任务、版本迁移与旧数据预览导入。
3. **建立服务与主动记忆工具**：保存、查看、更正、忘记；先验证确定性行为。
4. **实现轮次提取和幂等任务**：fake provider 先验证，再接真实模型；所有失败可检查。
5. **实现检索和预算组装**：先关键词闭环，后真实 embedding；保持来源和诊断信息。
6. **接回聊天流程并做 smoke**：防止重复提取和工具链破坏，补齐真实模型验证与用量记录。

M1 完成时应交付：

- [x] 可运行的聊天记忆功能与主动管理工具。
- [x] 配置说明、数据目录和迁移/回滚步骤。
- [x] 离线回归结果及带来源的小型检索验证集。
- [x] 真实模型 smoke 的运行配置、模式、结果和失败记录。
- [x] 尚未实现的功能清单，以及 M2/M3 的后续任务。

开发过程中优先回答三个问题：**这条记忆从哪里来、现在是否仍有效、为什么本次被召回。** 能稳定解释这三点，后续增加摘要、离线整理和程序经验才有可靠基础。
